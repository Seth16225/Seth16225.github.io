RISC-V CPU Implementations in SystemVerilog

A progression of RV32IM processor designs, from a single-cycle datapath through a 5-stage pipeline to a pipelined core backed by an AXI4-Lite cache hierarchy. Every design is verified against the official riscv-tests suite and the Dhrystone benchmark, and synthesizes for the Lattice ECP5 FPGA on the ULX3S board.

Cycle count alone is misleading, and deliberately so. The single-cycle design retires an instruction every cycle, but instruction fetch, the ALU, and the data memory access all sit in one combinational path, so it only closes timing at 4.72 MHz. The pipelined design needs 34% more cycles — bubbles from branches and load-use hazards — yet finishes Dhrystone 5.7x faster, because splitting that path into five stages buys 7.6x the clock rate. That tradeoff is the whole point of the exercise.

Two other results worth reading off the table. The multi-cycle design gets most of the way there on its own, because it moves memory into a second, phase-shifted clock domain and off the critical path — the pipeline's remaining advantage over it is a more modest 1.15x. And the AXI-Lite version is slower than the pipeline it is built from: instruction fetch becomes a two-cycle round trip over the bus, adding a stage and making every branch misprediction cost an extra flush. Both are honest costs of the respective designs.

Fmax figures are post-routing from nextpnr-ecp5, taking the limiting clock domain (hw3 and hw4 are dual-clock designs).

Bypassing in the 5-stage pipeline

The pipeline implements MX, WX, and WD bypasses. MX takes priority over WX, since the Memory stage holds the more recent value:

hw5-pipelined/DatapathPipelined.sv 
// Bypasses
always_comb begin
  x_rs1_data = execute_state.rs1_data; // default unless bypassed
  x_rs2_data = execute_state.rs2_data;

  // MX bypass has priority
  if (memory_state.rd_we && (memory_state.rd != 5'd0) && (memory_state.rd == e_insn_rs1))
    x_rs1_data = memory_state.rd_val;
  // WX bypass
  else if (writeback_state.rd_we && (writeback_state.rd != 5'd0) && (writeback_state.rd == e_insn_rs1))
    x_rs1_data = writeback_state.rd_val;

  if (memory_state.rd_we && (memory_state.rd != 5'd0) && (memory_state.rd == e_insn_rs2))
    x_rs2_data = memory_state.rd_val;
  else if (writeback_state.rd_we && (writeback_state.rd != 5'd0) && (writeback_state.rd == e_insn_rs2))
    x_rs2_data = writeback_state.rd_val;
end

The WD bypass lives inside the register file, so that an instruction reading register x in Decode sees a write to x landing in Writeback that same cycle:

hw5-pipelined/DatapathPipelined.sv — RegFile 
// WD is needed when Decode reads a register before Writeback can write it
always_comb begin
  if (we && (rd != 5'd0) && (rs1 == rd))
    rs1_data = rd_data;
  else
    rs1_data = regs[rs1];

  if (we && (rd != 5'd0) && (rs2 == rd))
    rs2_data = rd_data;
  else
    rs2_data = regs[rs2];
end

The interesting one: the AXI-Lite cache

hw6-cache is the most substantial project here, and the one worth reading first. It has two halves.

AxilCache.sv — a direct-mapped, write-back cache

The cache is an AXI4-Lite subordinate on the processor side and an AXI4-Lite manager on the memory side. Capacity is parameterized by NUM_SETS; the tests exercise it at both 16 B (easy to debug) and 2 KB (what the processor uses).

The hard part is not the cache policy, it is the timing. To keep up with the pipeline the cache has to sustain one hit per cycle with no bubbles between back-to-back accesses, while still honoring AXI's valid/ready handshake in both directions. That means:

  • A hit is a single-cycle registered response: combinational tag compare, result registered out.
  • Consecutive hits keep ARREADY high so a new request lands every cycle.
  • When the manager is not RREADY, the cache must buffer one in-flight request and drop ARREADY to backpressure the next one — otherwise a response gets dropped on the floor.

Misses run a four-state machine:

hw6-cache/AxilCache.sv 
typedef enum {
  // cache can respond to an incoming request
  CACHE_AVAILABLE = 0,
  // cache miss, waiting for fill from memory
  CACHE_AWAIT_FILL_RESPONSE = 1,
  // cache miss, waiting for writeback to memory
  CACHE_AWAIT_WRITEBACK_RESPONSE = 2,
  // cache waiting for manager to accept response
  CACHE_AWAIT_MANAGER_READY = 3
} cache_state_t;

A dirty victim is written back first, then the block is filled, then the original request completes in the fill cycle rather than costing an extra replay.

DatapathPipelinedCache.sv — integrating it

Hanging a variable-latency cache off a pipeline is where the design decisions live:

  • Fetch sends a PC, not an instruction. The instruction bits arrive on RDATA a cycle later, so the Decode pipeline register carries only a PC and a valid bit; the bits themselves come straight off the bus. Branch misprediction squashes get correspondingly subtler — the mispredicted instruction is in flight on the bus, not sitting in a register.
  • Fetch is throttled to one outstanding request. A request only issues in a cycle where Decode frees up, and RREADY drops to make the memory hold RDATA across a stall. That single invariant makes stalls, squashes, and I$ misses all fall out correctly.
  • Load results arrive in Writeback. Load formatting (lb/lh/lw sign extension) moved from Memory to Writeback, which pushes the load-use stall from one cycle to two.
  • A D$ miss freezes the entire pipeline, including any division in flight in the divider pipeline.

The whole stall structure reduces to four wires:

hw6-cache/DatapathPipelinedCache.sv 
// a D$ miss freezes the whole pipeline
wire pipeline_frozen = dmem_stall;
// F and D also freeze for load-use and div hazards
wire fetch_decode_stall = pipeline_frozen || stall_from_load || stall_for_div;
// waiting on insn bits from imem
wire imem_wait = decode_state.valid && !icache.RVALID;
// D frees up this cycle, so we can take a response and send the next fetch
wire d_advance = !fetch_decode_stall && !imem_wait;

Two notes on the numbers, because a portfolio with unexplained failures is worse than one that explains them:

The two miss-path failures are testReadMissWait and testReadMissAfterWaitingHit, which require a 2-cycle miss. The Python AxiLiteRam used by those tests takes 2 cycles to respond (measured: request sampled at t=13, data back at t=17), where the SystemVerilog AxilMemory the processor actually uses takes 1. Meeting them would mean forwarding both the request and the fill combinationally, which makes a D$ miss free and breaks every processor test that expects a 2-cycle miss penalty. The two are mutually exclusive; the processor timing wins.

The I$+D$ configuration is a bonus config the graded suite does not include. All 46 riscv-tests binaries pass there — every failure is a cycle-count expectation, not a wrong result. The test formulas charge one I$ miss for programs with several independent ones (4-byte blocks mean consecutive instructions live in separate blocks), and the "a D$ miss stalls all prior stages" rule is one cycle stricter than those particular expectations.

Running it

Everything runs in the course Docker image, which bundles Verilator, cocotb, Yosys, and nextpnr. 

# one-time: decompress the Dhrystone reference traces
./setup.sh

# run a project's full test suite
docker run --rm -v "$PWD":/work -w /work/hw6-cache cis5710/hw-base-arm:latest \
  bash -c 'source /tools/oss-cad-suite/environment; pytest -q -s testbench.py'

Inside the container, or with Verilator + cocotb locally:

cd hw6-cache
pytest -q -s testbench.py                                  # everything
pytest -q -s -k runCocotbTestsDmCacheHitSmall testbench.py # one suite
pytest -q -s testbench.py --tests testLoadUse1,testWM      # specific cases

FPGA synthesis and place-and-route, which reports utilization and Fmax:

cd hw6-cache && make resource-check

Waveforms are written to sim_build/dump.fst and open in GTKWave or Surfer.

What is mine and what is not

Worth being explicit about, since this is coursework.

Course-provided scaffolding, written by the CIS 5710 staff:

  • All testbench*.py files, the reference trace-*.json files, and common/python/
  • AxilMemory and EasyAxilMemory (the memory models behind the caches)
  • system/System.sv FPGA wrappers, common/make/fpga.mk, board constraints, docker/
  • The per-project README.md files, which are the original assignment writeups

Third-party: riscv-tests/ is the official RISC-V test suite (BSD licensed, from riscv-software-src/riscv-tests).

Everything else — the datapaths, the divider, the CLA, AxilCache.sv — is my implementation, filling in TODO-marked skeletons the staff provided.
